\subsection{Schéma}

Nous avons construit l'API GraphQL avec Graphene-Django~\cite{graphene}, en suivant la spécification GraphQL~\cite{graphqlspec}. Elle n'a qu'un seul point d'entrée, \code{POST /graphql/}. Chaque application déclare ses types, ses requêtes et ses mutations dans son propre \code{schema.py}, et le schéma racine les assemble par héritage multiple.

\begin{lstlisting}[language=Python,caption={Assemblage du schéma (\texttt{config/schema.py}).},label={lst:schema}]
class Query(itinerary.Query, trips.Query, accounts.Query, graphene.ObjectType):
    pass


class Mutation(itinerary.Mutation, trips.Mutation, graphene.ObjectType):
    pass


schema = graphene.Schema(query=Query, mutation=Mutation)
\end{lstlisting}

Les types \code{User}, \code{Trip}, \code{TripParticipant}, \code{Destination} et \code{Activity} héritent de \code{DjangoObjectType}. Chacun a sa liste blanche de champs. Par exemple, le type \code{User} ne montre ni le mot de passe ni les droits d'administration, et le courriel n'est visible que par son titulaire. Les choix des modèles deviennent des énumérations GraphQL (\code{TripStatus}, \code{ParticipantRole}, \code{ActivityCategory}). Les données externes ont leurs propres types, \code{Weather}, \code{CountryInfo} et \code{DestinationOverview}.

\subsection{Réutilisation de la logique REST}

Nous n'avons réécrit aucune règle pour GraphQL. Tous les resolvers partent de \code{Trip.objects.visible_to(user)}. Les mutations réutilisent les serializers DRF (et donc \code{Model.clean()} et les contraintes) ainsi que les services (\code{create_trip}, \code{clone_trip}, \code{add_participant}). Les permissions objet sont les mêmes classes qu'en REST. Chaque mutation tourne dans une transaction (\code{@transaction.atomic}).

\begin{lstlisting}[language=Python,caption={Mutation de modification (\texttt{apps/trips/schema.py}, extrait).},label={lst:mutation}]
class UpdateTrip(graphene.Mutation):
    class Arguments:
        id = graphene.ID(required=True)
        input = TripUpdateInput(required=True)

    trip = graphene.Field(TripType)

    @classmethod
    @transaction.atomic
    def mutate(cls, root, info, id, input):
        trip = get_or_not_found(visible_trips(info), TRIP_NOT_FOUND, pk=id)
        check_object_permission(info, IsTripEditor, trip)
        serializer = TripSerializer(trip, data=dict(input), partial=True,
                                    context=serializer_context(info))
        return cls(trip=reload_trip(info, save_serializer(serializer)))
\end{lstlisting}

\subsection{Authentification, limites et erreurs}

La vue \code{TravelHubGraphQLView} hérite de \code{GraphQLView}. Comme pour l'API REST, elle vérifie le jeton avec la classe \code{JWTAuthentication} de SimpleJWT. Sans en-tête, la requête est anonyme et chaque champ protégé répond \code{not_authenticated}. Un jeton invalide ou expiré donne un 401. La vue ne tient jamais compte du cookie de session, c'est pour ça qu'on peut l'exempter de la protection CSRF sans risque. Les limites de requêtes utilisent les classes et les compteurs de DRF. Un utilisateur a donc un seul quota pour REST et GraphQL.

Les erreurs gardent le code et les détails de l'erreur REST équivalente dans le champ \code{extensions}. Si l'erreur est inattendue, son message n'est pas montré. Elle devient \code{internal_error} et sa trace est journalisée.

\begin{lstlisting}[language=json,caption={Erreur de validation d'une mutation \texttt{updateTrip}.},label={lst:graphql-erreur}]
{
  "errors": [{
    "message": "Les données envoyées sont invalides.",
    "path": ["updateTrip"],
    "extensions": {
      "code": "validation_error",
      "details": {"endDate": ["La date de fin doit être postérieure ou égale à la date de début."]}
    }
  }],
  "data": {"updateTrip": null}
}
\end{lstlisting}

\subsection{Durcissement et performance}

Trois paramètres, relus à chaque requête, protègent le point d'entrée. \code{GRAPHQL_MAX_DEPTH} limite la profondeur des requêtes à 6, ce qui bloque les requêtes cycliques (\texttt{trip \{ destinations \{ trip \{ \ldots{} \} \} \}}) avant qu'elles s'exécutent. \code{GRAPHQL_INTROSPECTION} ferme l'introspection (\code{__schema}, \code{__type}) en production, mais laisse passer \code{__typename}, que des clients comme Apollo ajoutent à chaque requête. Enfin, avec \code{GRAPHQL_GRAPHIQL}, l'interface GraphiQL n'est servie qu'en développement.

Pour la performance, \code{myTrips} et \code{trip} préchargent les destinations, les activités ou les participants seulement si ces champs sont demandés. La fonction \code{selected_fields()} parcourt la sélection, fragments compris. Le nombre de requêtes SQL ne dépend donc pas du nombre de voyages renvoyés. \code{myTrips} est paginée comme l'API REST, avec 20 éléments par défaut et 100 au maximum.

\subsection{Exemple}

La requête de l'extrait~\ref{lst:graphql-requete} récupère en un seul aller-retour les voyages planifiés, leurs destinations, la météo actuelle et la fiche de chaque pays. En REST, il faudrait une requête pour la liste, puis deux requêtes par destination.

\begin{lstlisting}[language=graphql,caption={Requête GraphQL qui regroupe plusieurs ressources.},label={lst:graphql-requete}]
query MesVoyagesPlanifies {
  myTripsCount(status: PLANNED)
  myTrips(status: PLANNED, orderBy: START_DATE, limit: 5) {
    id
    title
    startDate
    totalCost
    destinations {
      city
      weather { current { temperature description } }
      countryInfo { name emoji currencies }
    }
  }
}
\end{lstlisting}

En développement, on peut écrire ces requêtes dans GraphiQL (figure~\ref{fig:graphiql}). L'explorateur à gauche liste les champs racine du schéma et aide à construire la requête. Le jeton se met dans l'onglet \emph{Headers}.

\subsection{Comparaison REST et GraphQL}

Le tableau~\ref{tab:rest-graphql} compare les deux API telles que nous les avons faites dans TravelHub. REST, au sens de Fielding~\cite{fielding2000}, organise l'API autour de ressources qui ont chacune leur adresse. GraphQL l'organise autour d'un schéma typé que le client interroge.

\begin{table}[htbp]
  \centering
  \small
  \caption{Comparaison des deux API de TravelHub.}
  \label{tab:rest-graphql}
  \begin{tabularx}{\linewidth}{@{}>{\raggedright\arraybackslash}p{3.0cm} X X@{}}
    \toprule
    \textbf{Critère} & \textbf{REST (DRF)} & \textbf{GraphQL (Graphene)} \\
    \midrule
    Points d'entrée & Une URL par ressource et par action (18 chemins) & Un seul, \code{POST /graphql/} \\
    Forme de la réponse & Décidée par le serveur (serializer) & Choisie par le client, champ par champ \\
    Trop ou pas assez de données & La liste n'a pas le détail. Nous avons ajouté \code{overview} pour éviter les allers-retours & Le client demande exactement les champs qu'il veut \\
    Erreurs & Code HTTP (400, 403, 404\ldots) et enveloppe \code{error} & HTTP 200 et liste \code{errors} avec \code{extensions.code}, 400 pour une requête invalide \\
    Échec partiel & Tout ou rien, sauf \code{overview} (\code{warnings}) & Prévu par GraphQL. Un champ en échec vaut \code{null} et les autres sont servis \\
    Cache HTTP & Possible sur les \code{GET} (URL stables) & Difficile, car tout passe par \code{POST} \\
    Documentation & OpenAPI, Swagger UI, ReDoc & Schéma typé et GraphiQL, introspection fermée en production \\
    Pagination & Numéro de page (\code{?page=}) & \code{limit} et \code{offset}, avec \code{myTripsCount} \\
    Risques propres & Champs exposés en trop (affectation de masse) & Requêtes coûteuses. Profondeur limitée à 6, mais largeur non limitée \\
    Authentification, permissions & JWT, \code{visible_to()}, classes de \code{apps.core.permissions} & Les mêmes, avec un quota partagé avec REST \\
    Validation & Serializers, \code{Model.clean()}, contraintes & La même, les mutations appellent les mêmes serializers \\
    \bottomrule
  \end{tabularx}
\end{table}

Pour nous, les deux API ne sont pas en concurrence, elles se complètent. REST est pratique pour les opérations simples et pour les autres applications qui voudraient se brancher, grâce au cache HTTP et à OpenAPI. GraphQL sera plus pratique pour les écrans du front-end qui affichent plusieurs ressources à la fois. Offrir les deux ne coûte pas cher, puisque toute la logique est partagée.
