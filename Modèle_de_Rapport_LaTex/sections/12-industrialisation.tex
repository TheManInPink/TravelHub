\subsection{Docker}

Le \code{Dockerfile} construit l'image en deux étapes. La première installe les dépendances dans un environnement virtuel, à partir de \code{python:3.14-slim}. La seconde copie cet environnement dans une image d'exécution sans outils de construction. L'image exécute \code{collectstatic} : WhiteNoise sert ensuite les fichiers statiques. Gunicorn tourne sous un utilisateur non privilégié, qui ne peut écrire que dans \code{/app/logs}. Une instruction \code{HEALTHCHECK} interroge \code{/health/} toutes les 30~secondes.

Le fichier \code{docker-compose.yml} assemble trois services (tableau~\ref{tab:compose}).

\subsection{Intégration continue}

Le flux GitHub Actions (\code{.github/workflows/ci.yml}) s'exécute à chaque \emph{push} sur \code{master} et à chaque \emph{pull request}. Il comporte deux tâches.
\begin{enumerate}
  \item \textbf{Lint et tests.} Un service PostgreSQL 18 démarre, puis Ruff vérifie le code et son formatage. Pytest s'exécute ensuite avec le seuil de couverture de 80\,\%. Le résumé de couverture s'affiche dans la page de l'exécution, et les rapports sont publiés comme artefacts.
  \item \textbf{Image Docker.} L'image est construite avec un cache, puis démarrée par \code{docker compose up --wait}. La tâche vérifie enfin que \code{/health/}, \code{/api/docs/} et \code{/api/schema/} répondent.
\end{enumerate}

Dependabot propose chaque semaine les mises à jour des dépendances pip et des actions GitHub.

\subsection{Journaux et contrôle de santé}

Chaque événement produit une ligne JSON, sur la console et dans un fichier rotatif (10~Mo, 5~archives). L'intergiciel \code{RequestIdMiddleware} attribue à chaque requête un identifiant, repris dans toutes ses lignes de journal et renvoyé dans l'en-tête \code{X-Request-ID}. Une erreur signalée par un utilisateur se retrouve ainsi en une recherche.

\begin{lstlisting}[language=json,caption={Ligne de journal d'une requête.},label={lst:log}]
{"timestamp": "2026-10-23T22:01:39.510+00:00", "level": "INFO", "logger": "travelhub.request",
 "message": "GET /api/trips/ 200", "request_id": "292f04c8d5e541e69c07c7565e0e65f0",
 "method": "GET", "path": "/api/trips/", "status": 200, "duration_ms": 401.1, "user_id": 5}
\end{lstlisting}

Le point d'accès \code{/health/} vérifie la base (\code{SELECT 1}) et le cache (écriture puis relecture). Il répond 200 si tout fonctionne, 503 sinon, sans divulguer la cause, qui est journalisée.

\subsection{Sauvegarde et restauration}

Les scripts \code{scripts/backup.ps1} et \code{scripts/restore.ps1} s'appuient sur \code{pg_dump} et \code{pg_restore}, pour la base locale comme pour celle du conteneur. Chaque archive est relue avant d'être conservée, et seules les sept plus récentes sont gardées. La restauration s'exécute en une seule transaction : une archive corrompue laisse la base inchangée. Une base non vide n'est écrasée qu'avec l'option \code{-Force}. La procédure de vérification restaure la dernière sauvegarde dans une base neuve, puis contrôle le schéma avec \code{migrate --check}.
